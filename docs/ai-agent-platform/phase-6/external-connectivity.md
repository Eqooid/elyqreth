Current implementation and exact executed results are recorded in [verification evidence](verification-evidence/external-connectivity-verification.json). This is hardening of the existing observation tier, not production activation, a provider deployment, a webhook or a new identity protocol.

**User decision:** no approved LangGraph production target exists; keep production activation closed. `NODE_ENV=production` still rejects enabled external profiles. Named local/OIDC account installations cannot mint legacy internal source grants. No authenticated browser account, proxy header or development credential bypasses this rule. ## Endpoint trust and outbound security

Use the existing endpoint object `{origin, network, allowedAddresses}`. Origin must be canonical HTTP(S) with no path, query, fragment, URL credentials, wildcard or alternate authority encoding. Public policy requires HTTPS. WHATWG URL validation bounds explicit ports; port zero is rejected. The local policy is explicit reviewed loopback/RFC1918/ULA addresses, not unrestricted internal access. Plain HTTP is supported only by the existing closed development/test tier; it is not approved production transport.

Every DNS answer must be a valid family-matching address in the exact configured pin set (at most 16). The actual request connects to one approved IP, preserves canonical Host/SNI and verifies the connected peer. Late DNS after abort opens no socket. All redirects fail before a second request; there is no credential forwarding or automatic destination expansion. Proxy environment variables are not used by these native clients; deploying through a forward proxy would need a separately reviewed contract, not a silent bypass.

Public policy already excludes private/link-local/CGNAT/mapped/NAT64/multicast/documentation/reserved addresses. Explicit private policy now additionally excludes AWS `fd00:ec2::/32`, Google metadata `fd20:ce::254`, and Azure WireServer `168.63.129.16`, including equivalent IPv6 spellings. These are platform services, not approved external orchestrators. See primary references: [AWS platform service range](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-route-tables.html), [Google metadata endpoints](https://docs.cloud.google.com/compute/docs/metadata/overview), [Azure WireServer](https://learn.microsoft.com/en-us/azure/virtual-network/what-is-ip-address-168-63-129-16). This is not an exhaustive guarantee about every cloud/control-plane address: review destination pins and preserve host/provider egress controls. No tests contact actual cloud metadata services.

TLS always uses `rejectUnauthorized=true` and explicit certificate-hostname verification. There is no per-profile insecure-certificate flag. A private CA, if needed for an explicitly reviewed future target, belongs in Node's backend trust configuration and image/runtime review; do not disable verification. New tests use `NODE_EXTRA_CA_CERTS` only in an isolated child process with a temporary test certificate. They prove actual TLS/key-header behavior against a synthetic local endpoint, not a live hosted provider.

## Credentials, binding and rotation

`credentialRef` names an `EXTERNAL_SECRET_[A-Z0-9_]{1,80}` backend value. Referenced secrets must be 8..4096 printable ASCII bytes. Each configured connection needs a distinct reference and credential value; aliases with the same value are also rejected. An uncredentialed local development profile remains possible under the existing policy. The approved LangGraph public profile requires a key reference. Missing referenced credentials fail before adapter or socket work.

Reuse T05's `EXTERNAL_SECRET_<NAME>_FILE` support: choose a direct value **or** file, never both. Linux production secret-file rules remain root/application ownership, no world reads or group/world writes, immediate `/run/secrets` paths. Loading an external key file does not permit enabling production external profiles. Secrets remain backend-only, never frontend configuration/build arguments/argv/URLs/public DTOs/health/logs. Direct environment injection remains compatible but may be visible to privileged process/container inspection; file mounts are not encryption or a secret manager.

A private hash binds connection ID, owner, adapter, namespace, generation, enabled/mode, endpoint/pins, capabilities, credential reference and current credential value. Cosmetic name changes and order of pins/capabilities do not alter security authority. The hash stays internal, never in session metadata or public diagnostics. Operations capture their credential once and validate the current binding before each transport call and after awaited negotiation/result. The observation service also rechecks the operator source grant after awaited discovery/result reads. Removed or replaced policy/credentials reject stale operations; they cannot combine a new credential with an old captured destination.

Opaque source sessions remain process-local, five-minute approvals tied to the existing development operator credential. Full connection/credential binding is now checked at each service boundary, after the advisory lock and again after asynchronous transaction work before commit. A revocation detected at that boundary rolls back the receipt/mapping/audit together. An already-sent request or already-committed receipt cannot be retroactively revoked; provider-side revocation and persisted history are separate facts.

Rotation procedure: stop the explicit observation caller, provision the replacement connection-scoped provider key externally, replace the protected value/file, retain connection/namespace/generation for the same provider identity, replace the process/configuration, obtain fresh operator/source grants, then health/observe/replay a known mapped run. Revoke the old key at the provider and verify it is rejected. There is no hot reload, dual-key overlap window or platform credential issuance. Old process sessions cannot be passed to a new process. Retiring/recreating a provider identity requires the existing generation/tombstone workflow; do not reset identity just to rotate a key.

## Trusted receipt, replay and lifecycle

Authentication and envelope validation precede durable acceptance. The existing closed validators reject unknown keys/types/event kinds, getters, custom prototypes, hidden properties, malformed IDs/timestamps/sequences and unsafe strings. The normalized encoded envelope is bounded to 12KiB and checked for configured secrets. There is no arbitrary nested metadata merge or executable deserialization. The generic API/edge body cap remains 64KiB but does not create an ingestion route or replace the smaller internal envelope limit.

Receipt deduplication uses persisted source incarnation + event ID and a canonical content hash excluding receipt time. Identical concurrent delivery has one effective receipt and acceptance audit; conflicting content for the same identity is rejected. Receipt commits independently of projection, so projection persistence failure can return durable deferred acceptance and explicit replay can recover it. An authorization failure or disconnect after receipt commit can still leave an accepted receipt; obtain fresh authority and inspect/retry the same event identity rather than assuming nothing committed. SQL locks, constraints and existing immutable audit are retained. No migration or new inbox/outbox is introduced.

Only approved ordering domains and exact arbitrary-precision source sequences can advance the observation. LangGraph uses documented local **phase ranks**, not invented provider event revisions: unknown 0, queued 1, running 2, terminal 3. Lower phases are stale; equal/conflicting or terminal-changing evidence is deferred. Unknown/resumable states remain representable. No historical events, cancellation or success are synthesized after outages or receipt-time changes. Duplicate polling is not evidence of a fresh provider observation.

There is no signed webhook, nonce or signed-request validity-window protocol to test. Durable idempotency is not cryptographic freshness, and provider lifecycle phase ordering is not a complete temporal history. Do not expose `authorize` or a generic normalized-envelope POST as a webhook. Any future ingress protocol needs a separate explicit source-principal/raw-byte/signature/replay contract and evidence before routing it through the edge.

## Failure isolation, retries and diagnostics

Process-global adapter-operation and transport-request concurrency remains four; it is not a fleet-wide limit across separately launched CLI processes. A single connection can occupy at most two in either layer, leaving capacity for a different connection. Maps are bounded by occupied slots and delete entries at settlement. A reviewed adapter or DNS lookup that ignores cancellation retains its occupied slot until actual settlement, preventing repeated timeouts from creating unbounded underlying work. Two fully stalled connections can still consume the global limit; explicit capacity rejection is a safe bounded outcome, not a promise of infinite availability.

One-shot observation commands and transport make **zero automatic retries**. Authentication/configuration/unsupported operations do not retry; safe retryable error classification is advisory. There is no background polling storm, unbounded queue, automatic exponential loop or external mutation retry. The current small manual observation tier needs bounded slots/deadlines rather than an additional circuit-breaker framework. If scheduling is introduced later, connection-scoped rate budgets/backoff/jitter/cooldown must be reviewed before enabling it. A 429 is normalized; no unsupported provider retry delay is invented. Dispatch/cancel remain disabled, so ambiguous mutation outcomes cannot cause duplicate remote dispatch here.

Existing `external.operation` logs carry safe connection/adapter/operation/mode/correlation, latency and outcome/error code. `external.ingestion` logs accepted/duplicate/rejected/projection-failed categories without payloads. Durable receipt history and audit provide bounded replay/backlog evidence. No new public diagnostics, credential fingerprint, raw HTTP body/header, provider result, general metric exporter or monitoring platform is introduced. Last accepted observation/freshness are read through existing authorized activity APIs; health failure does not mark an external Execution failed.

## Edge, native drain and restart

The T06 TLS edge's existing controller-family allowlist excludes external-events/mappings/adapter/admin/webhook routes. Internal `/ready` remains namespace-only and public `/health` minimal. Only edge publishes approved test/production ingress ports; provider commands, API, database and maintenance remain private. T10 creates no ingress location, public provider proxy, worker or messaging service.

Native-only T09 drain closes native admission, not provider authority or trusted external persistence. The new PostgreSQL test applies concurrent duplicate observations while native admission is closed and proves no native Execution is created. Existing full runtime drain and mixed-activity tests remain active. Full process termination stops the internal caller; already committed inbox evidence remains durable and fresh authorized grants resume bounded explicit replay after restart. External providers remain authoritative throughout.

## Verification and known limits

`npm.cmd run test:api` includes endpoint/credential/binding/capacity tests and actual pinned HTTPS sockets with temporary certificates. OpenSSL is an existing local/container verification prerequisite (CI Ubuntu provides it; Windows uses the existing Git OpenSSL path). Temporary test keys are never committed. TLS fixtures validate transport/auth behavior, not a real hosted provider.

`npm.cmd run test:database-roles` exercises new precommit revocation rollback, connection-scoped concurrent duplicates during drain and rotation/restart replay through actual restricted runtime grants. `npm.cmd run test:db` includes the complete existing ingestion/order/mapping/projection/auth/native/city contracts. The container harness also loads a synthetic EXTERNAL_SECRET file as non-root under production file permissions without enabling an integration, denies ambiguous value/file configuration, and checks image history for the secret. `node scripts/container-hardening.mjs --edge --runtime-drain` validates existing private edge/session/browser/readiness/Compose/drain boundaries against rebuilt images. No paid API or production database is required.

Unsupported signatures/webhooks, dispatch/cancel, hosted target verification, automatic provider scheduling and production principal activation are explicit limits, not passing tests. T11 Observability & Production Runbooks remains the next roadmap task and is not implemented here.
