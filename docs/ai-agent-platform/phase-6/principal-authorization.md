## Actual principal model

| Concept | Implemented identity / authority | What it does not imply |
| --- | --- | --- |
| Authenticated local principal | Shared `assertLocalRequest` verifies actual loopback transport, host, allowed Origin and exact constant-time bearer credential. Returns frozen `LocalPrincipal` with LOCAL_CREDENTIAL kind, configured owner, explicit operator/city-read/interaction/collaboration-read audience and safe local actor reference | Not a named human, account, tenant, session or production JWT principal |
| Resource owner | Existing `owners.id`, persisted on Agent/route/Task/Execution/collaboration/mapping/event records; local owner is backend configuration, never a request claim | Not automatically an authenticated user or JWT subject; owner rows are not an account/login database |
| Execution actor | Persisted Agent/Task/Execution/orchestrator IDs, factory-owned execution context and committed runtime lease/fencing | Agent ID is not a user credential; copying an execution context cannot grant tool authority |
| Trusted service authority | Existing in-process coordinator uses persisted owner/correlation/claim; tools revalidate factory origin, configured binding/capability and committed claim; local recovery and CLI preserve scope | No independent worker identity/queue consumer exists; arbitrary job messages or owner IDs grant no service privilege |
| External source identity | Opaque source session minted by IngestionAuthority after local operator proof, bound to owner/connection/namespace/generation/expiry/kind; checked again inside the DB transaction | Provider Agent/run/event IDs and metadata are not local principals; ingestion grants cannot become mapping/operator grants |
| Named application principal | LOCAL_ACCOUNT from verified password/session or OIDC from verified access JWT and explicit subject mapping; operator/viewer role, server-selected existing owner and request-bound identity | Not public self-registration or tenant ownership; cookies/proxy headers do not authenticate |

Principal identity, resource ownership and execution actor are deliberately separate. Local safe actor references identify a shared credential audience, not individual human attribution. Existing persisted audit labels remain intact; the typed verifier result is not a new audit store or authorization framework. A small user-authorized local account/session schema is added; no new RBAC/ABAC engine, identity server, public tenancy or sharing model is introduced.

## Request authentication and scoped delegation

The selected account mode first authenticates through the global AuthenticationGuard and creates a request-bound AccountPrincipal. Existing object guards consume that verified principal, check viewer/operator eligibility and keep their ownership/parent/version/lifecycle predicates. There is no account-to-development-token fallback. See the [mode guide](authentication-modes.md) for exact JWT/session validation and principal attribution. The following local audience pipeline remains the legacy mode when AUTH_MODE is disabled.

`common/local-access.guard.ts` remains the shared verifier for all current HTTP credential audiences. After successful verification it resolves **only a configured audience** and backend registry owner; even a caller-selected matching secret is rejected if it is not a configured audience. It ignores user/owner/tenant/forwarded identity headers and cookies. Remote socket/Host/Origin checks are independent of credential equality. Unknown/missing credentials cannot fall back from a browser audience to operator authority.

The global InteractionGuard validates the exact route and owned/eligible Agent/Task/Execution before issuing a scoped interaction grant. It now derives owner from the verified principal. Existing private async-context storage retains the Agent/operation grant; a second private WeakMap binds it to the exact request object, method and path. Nothing is attached to caller-controlled request metadata or the logged request context. LocalAccessGuard no longer accepts the mere presence of an async interaction scope: it requires the same request/route and revalidates current token, local restrictions, owner and configured Agent grant. Copying a request or inheriting an async scope cannot authorize another request or an administrative route. Unbound scopes used in trusted internal unit fixtures are not HTTP credentials.

This fixes a confirmed overly broad authorization shortcut and adds defense in depth around currently immutable configuration. It is **not evidence of a demonstrated remote exploit** in the prior exact-route pipeline. No successful real HTTP request is advertised as a production principal. Local shared bearer credentials have no per-person revocation/session lifetime; operator rotation/restart and browser disconnect are the current mechanisms.

## Authorization matrix

Rows describe existing operations and ownership constraints. Named operator principals use supported mutations; named viewers use authorized reads. Legacy loopback audiences retain their narrower original grants. Production business operations remain closed when account mode is disabled; enabled modes require explicit validated configuration and later deployment security gates. "Owner" means backend-resolved existing owner, not an ID supplied by the requester. No tenant beyond existing owner scope is claimed.

Permissions here describe actual audience/operation gates, not new role names. Services continue using existing scoped repositories and owner predicates, composite DB constraints, transaction locks, lifecycle guards and safe serializers. A resource ID, parent link or pagination cursor never authenticates its caller. Lists scope before limit/offset/cursor. No source lifecycle ownership is changed.

## Service, runtime and external authority review

`runtime/runtime-persistence.service.ts` loads the owner-scoped Task and intended Execution, validates Agent/route/native snapshot, verifies committed claim token and persists terminal outcomes through the existing state machine. Admission/finalization/tool checks reject mismatched owner/Agent/Task/Execution and stale leases. Recovery preserves original persisted identity; no arbitrary unverified queue/job input is accepted. There is no separate worker endpoint to authenticate in this repository. Crash uncertainty remains fenced and visible; this task does not claim automatic exactly-once external effects.

`ExternalAdapterService` verifies owner/connection/operation and compiled capability intersection. Internal access objects are trusted application inputs, not public authentication DTOs. `IngestionAuthority` issues unforgeable WeakMap-backed grants, checks credential rotation, kind/expiry and current connection generation/enabled state. `ExternalIngestionService` checks again in the transaction after ownership locking and validates durable orchestrator registration, external mapping and collaboration correlation. External metadata cannot select an owner, create a user principal or mutate native Execution state. Existing database constraints and source-scoped uniqueness provide independent integrity checks. No new adapter or webhook path is added.

## Polling, reconnection and frontend behavior

Existing synchronization is authenticated bounded polling, not SSE/WebSocket. Each poll re-enters current guards. A cursor is an ordering/recovery hint, not a credential; cross-resource/corrupt/future cursors are rejected or require a snapshot. Distinct limited browser audiences remain independent, with session generations, abort/late-response rejection, authorization cleanup and disconnect on loss of credentials. Logout/expiry here means existing local token disconnect/revocation behavior, **not an implemented OIDC browser session**. T04 owns production browser session/CSRF integration.

Existing frontend tests cover cached-state clearing, owner/Agent switch, denial handling, reconnect, duplicate/out-of-order events and teardown; browser fixture/integration coverage exercises the real NPC collaboration inspection. No frontend or Canvas source is changed by T03. There are no subscriptions that can bypass a new polling authorization check.

## Error and audit contracts

Transport denial remains 401 for invalid credentials, 403 for recognized but forbidden transport/route/audience and 404 for disabled features or inaccessible resources. Endpoint-specific runtime/collaboration errors preserve existing safe code mappings; invalid filters/cursors and conflicts keep their existing 400/409 semantics. Exact-route limited scopes cannot become operator authentication. No raw tokens, JWTs, key material, user-supplied identity headers or provider payloads are added to logs/errors.

Existing audit persists owner/resource/correlation/command outcome and safe local operator, interaction, runtime or external-source references. It does not fabricate named human attribution. Legacy shared local operator audit cannot distinguish people. Account/OIDC login and initiating Agent/Task/Execution/collaboration commands now carry stable local-user UUID or issuer/subject hash references; runtime/source service attribution remains distinct. No new audit table/event mechanism or global administrative principal is introduced.

## Backend modes and remaining deployment gates

The [authentication guide](authentication-modes.md) defines exclusive AUTH_MODE=local or oidc, a reviewed existing owner, viewer/operator permission policy, local provisioning/revocation and OIDC public-key/subject configuration. No public provider or default credential is provisioned. Real local Keycloak tokens are used for acceptance; real installation values are not required to test the support, but missing/invalid selected-mode configuration fails startup.

Local accounts use durable opaque sessions and per-request revocation/credential-version checks. OIDC verifies explicit API access-token purpose, signature, issuer, audience, expiry and maximum age with pinned public keys; ID tokens and fallback credentials are rejected. Provider revocation/introspection and browser IdP logout are not claimed. The guide records rotation/restart and bounded JWT lifetime limitations.

Frontend OIDC authorization-code/PKCE, login screens, cookie/CSRF integration and production runtime-client mode are T04. Actual TLS/private networking, hosting/DB choice, production secret injection, operations, external connectivity and public-account acceptance remain later gates. No production rollout is authorized by backend acceptance.
